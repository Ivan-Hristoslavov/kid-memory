# PrintFactory — какво е API-то им и какво НЕ е

Прочетено на 2026-09-11 от помощния им център, категория „Интеграции"
(`/index.php?route=extension/pf_help/category&pf_help_category_id=1`, статии
51–59). Записано, за да не се търси втори път и за да е ясно какъв е въпросът
към тяхната поддръжка.

## Най-важното

**API каталогът им не е техният каталог.** Той е списъкът с готови продукти,
които един акаунт е подготвил на ръка. Техните ~150 артикула не се появяват през
API. Появява се това, което ти самият си направил в Дизайн студиото им.

Шестте стъпки, техни думи (статия 52):

```
1 Избери продукт   2 Създай дизайн      3 Запази
  от каталога        в Дизайн студиото    в Темплейти
                  ↓
4 API каталог     5 Настрой варианти   6 Публикувай
  добави продукта   размери и цветове    чрез интеграцията
```

> „Ако един продукт не е добавен в API каталога, той няма да бъде достъпен за
> синхронизация с външния магазин."

Първите три стъпки са човек пред браузър. Няма как да се автоматизират.

## Какво носи една поръчка

Изчерпателно, от статия 57:

| Поле | |
| --- | --- |
| Продукт | кой PF продукт |
| PF SKU | връзката магазин ↔ PF |
| Вариант | размер, цвят |
| Количество | |
| Получател | данни за доставка |
| Номер на поръчката | за проследяване |

**Няма файл. Няма URL. Няма дизайн.**

Това е огледалният образ на printondemand.bg. Там `/v2/crt-spd` приема PNG като
base64 и създава продукт — затова чаша със снимка изобщо може да съществува.
Тук дизайнът е замразен в SKU-то, преди поръчката да се появи.

### Какво следва от това за нашия магазин

| Наше | През тяхното API? |
| --- | --- |
| 163 готови дизайна (фиксирана щампа) | **да** — един PF SKU на дизайн × вариант |
| Чаша/постер/пъзел със снимка на клиента | **не** — снимката няма SKU |
| Надпис с име (`{name}` замяна) | **не** — всяко име е различна щампа |

Тоест „целият сайт да работи с техните продукти" се разпада на две. Готовите
дизайни — да, и това е истинска печалба: 163 артикула, които в момента се
произвеждат само от другата печатница, стават достъпни и при тях. Всичко
персонализирано — не, освен ако не отворят нещо като `crt-spd`. Това е въпросът
към поддръжката им и той е конкретен: *„има ли начин поръчка през интеграцията
да носи собствен принт файл, без продуктът да е минал през Дизайн студиото?"*

## Товарителницата е ръчна, нарочно

Статия 57: „Print Factory не генерира автоматично товарителницата вместо теб."
Причината им е разумна — не искат да те обвързват с куриер. Следствието за нас:
**поръчка към тях никога не е напълно автоматична.** `createOrder` праща
производството, после човек прави товарителницата с нашия куриер и я качва към
поръчката им. Админът трябва да го казва на глас, иначе ще се пропусне.

## Какво е известно и какво не

| | |
| --- | --- |
| Client Code | `pf_customer_2223` — от панела, Интеграции → WooCommerce |
| API Key | в `.env`, не тук |
| API URL | `https://printfactory.bg` |
| **Endpoint** | **неизвестен** |

Помощният им център описва payload-а и процеса и **никъде не публикува URL**.
Няма публичен API reference. Плъгинът за WooCommerce, който знае маршрута, е зад
клиентския вход, а в WordPress.org го няма.

Пробвано и изоставено: `/api/*` в няколко форми, `index.php?route=` с
`extension/pf_api/...`, `pf_integration`, `pf_woo`, `pf_sync`, `pf_catalog`,
`pf_order`, `pf_shopify`, плюс очевидните REST пътища и няколко адреса за
сваляне на плъгина. Всички връщат 404 на OpenCart. Сканиране на чужд сървър не е
начин да се научи това.

**Как се затваря:** свали плъгина от техния панел (Интеграции → WooCommerce) и
отвори кой да е `.php` файл в него — базовият URL и екшъните са там, в чист вид.
Стойността отива в `PRINTFACTORY_API_PATH`, имената на хедърите се сверяват в
`lib/pod/printfactory.ts::call`, и толкова.

Докато я няма, `PrintFactoryProvider.configured()` връща `false` — нарочно.
Доставчик, който изглежда наличен и се чупи след като клиентът е платил, е
по-лошо от доставчик, който честно го няма.

## Статуси

Тяхната номенклатура не е публикувана. `mapStatus` познава очевидните
(`new`/`processing`/`shipped`/`delivered`/`cancelled`) и връща `UNKNOWN` за
всичко останало, вместо да гадае. Статус, който кодът не познава, е статус, чието
значение не знае — а да покажеш „изпратена" за такъв е как клиентът разбира, че
пратката пътува, преди изобщо нещо да е отпечатано.
