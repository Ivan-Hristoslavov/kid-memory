# PrintFactory — какво е API-то им и какво НЕ е

Прочетено на 2026-09-11 от помощния им център, категория „Интеграции"
(`/index.php?route=extension/pf_help/category&pf_help_category_id=1`, статии
51–59). Записано, за да не се търси втори път и за да е ясно какъв е въпросът
към тяхната поддръжка.

## Най-важното

**API каталогът им не е техният каталог.** Той е списъкът с готови продукти,
които един акаунт е подготвил на ръка. Техните ~150 артикула не се появяват през
API. Появява се това, което ти самият си направил в Дизайн студиото им.

Шестте стъпки, техни думи (статия 52):

```
1 Избери продукт   2 Създай дизайн      3 Запази
  от каталога        в Дизайн студиото    в Темплейти
                  ↓
4 API каталог     5 Настрой варианти   6 Публикувай
  добави продукта   размери и цветове    чрез интеграцията
```

> „Ако един продукт не е добавен в API каталога, той няма да бъде достъпен за
> синхронизация с външния магазин."

Първите три стъпки са човек пред браузър. Няма как да се автоматизират.

## Какво носи една поръчка

Изчерпателно, от статия 57:

| Поле | |
| --- | --- |
| Продукт | кой PF продукт |
| PF SKU | връзката магазин ↔ PF |
| Вариант | размер, цвят |
| Количество | |
| Получател | данни за доставка |
| Номер на поръчката | за проследяване |

**Няма файл. Няма URL. Няма дизайн.**

Това е огледалният образ на printondemand.bg. Там `/v2/crt-spd` приема PNG като
base64 и създава продукт — затова чаша със снимка изобщо може да съществува.
Тук дизайнът е замразен в SKU-то, преди поръчката да се появи.

### Какво следва от това за нашия магазин

| Наше | През тяхното API? |
| --- | --- |
| 163 готови дизайна (фиксирана щампа) | **да** — един PF SKU на дизайн × вариант |
| Чаша/постер/пъзел със снимка на клиента | **не** — снимката няма SKU |
| Надпис с име (`{name}` замяна) | **не** — всяко име е различна щампа |

Тоест „целият сайт да работи с техните продукти" се разпада на две. Готовите
дизайни — да, и това е истинска печалба: 163 артикула, които в момента се
произвеждат само от другата печатница, стават достъпни и при тях. Всичко
персонализирано — не, освен ако не отворят нещо като `crt-spd`. Това е въпросът
към поддръжката им и той е конкретен: *„има ли начин поръчка през интеграцията
да носи собствен принт файл, без продуктът да е минал през Дизайн студиото?"*

## Товарителницата е ръчна, нарочно

Статия 57: „Print Factory не генерира автоматично товарителницата вместо теб."
Причината им е разумна — не искат да те обвързват с куриер. Следствието за нас:
**поръчка към тях никога не е напълно автоматична.** `createOrder` праща
производството, после човек прави товарителницата с нашия куриер и я качва към
поръчката им. Админът трябва да го казва на глас, иначе ще се пропусне.

## Протоколът

Няма публичен API reference. Всичко по-долу е прочетено от
`print-factory-api-v1.0.6.zip` — плъгинът им за WooCommerce, който се сваля без
вход от `https://printfactory.bg/pf_download_woocommerce.php` — и после сверено
срещу живата услуга.

Не е REST. Шест плоски PHP файла в корена на сайта:

| Метод | Endpoint | Какво прави |
| --- | --- | --- |
| GET | `pf_api_products.php` | API каталогът |
| GET | `pf_api_products_changed.php` | само променените от последната синхронизация |
| GET | `pf_api_mark_product_synced.php` | `?api_client_product_id=N` — потвърждаваш, че си го взел |
| POST | `pf_api_receive_order.php` | създава поръчка |
| GET | `pf_api_queue_status.php` | `?api_queue_id=N` или `?external_order_id=X` |
| POST | `pf_api_waybill_pdf.php` | закача нашата товарителница към тяхната поръчка |

**Автентикация.** Ключът се праща на две места едновременно, защото плъгинът го
прави така и отвън не се вижда кое от двете сървърът чете:

- хедър `X-PF-API-KEY: <key>` — при всяка заявка;
- query параметър `api_key=<key>` — при GET;
- в JSON тялото `{"api_key": ..., "client_code": ...}` — при POST.

Странично следствие: ключът влиза в техния access log като част от URL. Това е
тяхно решение и не се поправя от наша страна — но е още една причина да се
ротира, ако някога изтече.

**HTTP 200 не значи успех.** Всеки endpoint връща `{"ok": true|false, "error":
"..."}` и отказана заявка също се връща със статус 200. Тялото е авторитетът;
код, който гледа само `res.ok`, ще прочете „поръчката е приета" от отказ.

### Проверено на живо

```
GET /pf_api_products.php
{"ok":true,"api_client_id":17,"customer_id":2223,
 "client_code":"pf_customer_2223","auth_source":"woocommerce_api_client",
 "count":0,"products":[]}
```

Връзката работи, акаунтът е разпознат, **каталогът е празен** — точно каквото
пише в документацията им. Нищо не е подготвено в Дизайн студиото.

### Поръчка

```jsonc
POST pf_api_receive_order.php
{
  "api_key": "…", "client_code": "pf_customer_2223",
  "external_order_id": "<нашият номер>",
  "source": "menty",
  "items": [{
    "sku": "<PF SKU>",           // задължително
    "qty": 1,                    // задължително
    "size": "M", "color": "Черна",
    "print_type": "DTG",
    "design_file": "<URL>",      // ТЕХНИЯТ файл за ТОЗИ sku — виж по-долу
    "options": { … }
  }],
  "recipient": { "firstname", "lastname", "telephone", // задължителен
                 "address_1", "city", "postcode", "country" },
  "shipping": { "courier", "waybill_mode": "own_waybill_later",
                "waybill_pdf_url" }
}
```

Отговор: `api_queue_id` веднага, `order_id` по-късно, когато опашката се
обработи. Затова `getOrder` пази queue id-то — то съществува в интервала, в
който PF номерът още го няма.

Техният валидатор отказва в този ред: липсващи `items`, липсващ `items[].sku`,
липсващ `items[].qty`, липсващ `recipient.telephone`. Товарителница **не** се
изисква — нарочно, за да може да дойде по-късно.

### За `design_file` — най-важният детайл

Полето е URL и изглежда като вратата към персонализацията. Не е. Проследено през
плъгина: стойността идва от `_pf_design_file`, мета на продукта, записана при
синхронизация от записа на PF продукта. Тяхното изображение за тяхното SKU,
върнато им обратно. Никъде плъгинът не слага собствен файл на магазина там.

Дали техният worker би приел произволен URL в това поле е **единственият въпрос,
който си струва да им се зададе**, защото отговорът решава дали снимка на клиент
може изобщо да мине оттук.

## Статуси

Тяхната номенклатура не е публикувана. `mapStatus` познава очевидните
(`new`/`processing`/`shipped`/`delivered`/`cancelled`) и връща `UNKNOWN` за
всичко останало, вместо да гадае. Статус, който кодът не познава, е статус, чието
значение не знае — а да покажеш „изпратена" за такъв е как клиентът разбира, че
пратката пътува, преди изобщо нещо да е отпечатано.
